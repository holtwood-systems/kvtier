# 技术决策日志（2026-11-20/21 会话，面试行为面弹药）

> 每条：抉择点 → 选择 → 理由 → 证据/结果。讲"取舍"类行为题时从中取材。

## 1. 验证优先于修复（为什么先跑双臂而不是直接改代码）
**抉择**：main 声称已修 salt 与 staging，是信还是验？
**选择**：先做 main 双臂验证实验（~2h GPU），再决定是否进入修复。
**理由**：上游修复无独立验证证据；若直接修，可能修已修之物（#36115 教训：只欢迎
挂在真 bug 上的贡献）；验证本身无论结果都是可发表的证据。
**结果**：①确实修了、②确实没修——一半精力花在了刀刃上，另一半避免了无效工作。

## 2. 剂效-判定双层模型策略
**抉择**：复现上游 issue 用什么模型？
**选择**：0.5B 做多臂快扫、Qwen3-4B 做判定臂。
**理由**：竞争窗口尺度 ∝ 每页字节数（0.5B 的 12.3KB/token 可能触发不了 issue 量级的
窗口），但 0.5B 扫参数空间便宜 10 倍。可控实验 ≠ 最小模型。
**证据**：4B 判定臂复现 28% 命中率（issue 实况 34-41%），0.5B 同向。

## 3. 不在 WSL2/3060 上跑实验 0 试点
**抉择**：服务器失联 4h+，要不要本地 6GB 卡先跑起来？
**选择**：不跑，转离线产出。
**理由**：main 的 WSL2 补丁已失效需手工移植、本地无 CUDA 工具链、结果带 WSL2 混杂
因子过不了自家有效性门禁——2-4h 换一份不达标的数据是负期望。
**结果**：离线期产出链路文档/20 问题库/双结局故事/恢复 Runbook，服务器恢复后 0 损失续跑。

## 4. 修复排序：F4/F1 先行、F3 缓行
**抉择**：四个修复方案按什么顺序推进？
**选择**：F4（纯计数）与 F1（scandir 快照）先做成可审补丁；F3（写队列背压）保持设计态。
**理由**：F4/F1 无语义风险、改动面 25-53 行、独立可合入；F3 触碰队列语义（ack 按位
配对假设），需要 EXP-D 的含/不含对照护航。
**证据**：F1/F4/F2-a 补丁 19 离线测试绿。

## 5. 对外策略：给 #49226 补证据而非自开修复 PR
**抉择**：复现成功后，贡献路径选哪条？
**选择**：在报告者自己的修复 PR 下发独立复现数据。
**理由**：不抢功（竞争 PR 互相挡路的活案例：#49086→#50582）；数据型评论是维护者
最欢迎的形态；我们的复现恰好支持其修复面（buffer_only 免疫 + 容量介导）。
**配套**：4× 结构型是 #49226 不覆盖的新问题面，单独走新 issue。

## 6. 共享 GPU 而非串行等待
**抉择**：兄弟会话占着 22.5GB 跑 7B 基准，等还是共享？
**选择**：用户裁定 + 技术可行性确认后转 shared_20GB 模式。
**理由**：剩余 25.5GB 够 0.5B/4B 臂；主判据是计数器型（抗性能噪声）；TTFT 只看
两臂同条件 ratio；共居事实记入威胁有效性——**可解释的部分噪声好过无限期等待**。

## 7. 公开保留自己的误读
**抉择**："索引逐出"解读被证据推翻（实为查询超时零记账），怎么处理？
**选择**：三处文案修正 + 在数字库里保留"初版解读已被推翻"的标注。
**理由**：误读→证伪→修正的循环是方法论的一部分；藏起来才是损失。
**证据**：盘上文件数 == acked 计数（精确相等）+ 12 个 R 的 TTFT 聚在预算+prefill。

## 8. cu12x 重建而非动驱动
**抉择**：main 默认 torch 是 cu130，驱动 550 跑不了。
**选择**：换 cu126 变体重建 venv，不碰驱动。
**理由**：驱动是宿主的（容器无权）；cu128 在 550 上已被基线证实可跑；环境可逆、
影响面收敛在自己的 venv。
**教训**：依赖面的 CUDA 主版本兼容是静态审计盲区——diff 看代码接口，没人看轮子标签。
