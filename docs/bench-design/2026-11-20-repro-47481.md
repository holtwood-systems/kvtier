## 0. 结论先行

上游已经走完一轮：报告者三次复现基线 dip，并完成了同 commit 的
`cache` vs `buffer_only` 单次对比（min 命中率 66.3% → 74.5%）；外部复核者

1. 在**当前 main + 非 Mooncake 后端**上检验 dip 是否仍在（fast_file 的

2. **容量剂效双因子分离**：L2 与 L3 容量解耦扫描（§4 臂表 A3/A4），

## 1. 上游事实（issue/评论页面明确写的）

### 1.1 基线复现配置与现象（banfeb，2026-10-30 起）

- 环境：A40（46,068 MiB）单卡、Qwen3-4B FP16、双 Xeon 8358、756 GB 内存、
  mooncake-transfer-engine 0.3.4.post2（CUDA 包 0.3.13.post1）、TCP 无 RDMA。
- 基线 commit：main 快照 2026-10-27，对应上游
  `e4d4a9a7de5454cd8b854b21af723c2155a55a3d`（banfeb 2026-11-12 提供）。
- 容量：L1 = `--max-total-tokens 178752`；L2 = `--hicache-ratio 2
  --hicache-size 48`（GB），启动日志实测 `Allocating kv hierarchical KV host
  pool: 325568 tokens, 48.01 GB host memory`；L3 = Mooncake 48 GiB 内存
  segment + SSD offload；`--page-size 64`；Qwen3-4B FP16 每 token KV
  144 KiB（xiezhq-hermann 与 banfeb 双向核对的算术：
  325,568 × 147,456 B = 48.007 GB，10^9 字节口径）。
- 负载：上游内置 `benchmark/hicache/bench_multiturn.py`，40 clients ×
  20 rounds（800 请求），每轮每 client 1,024 新输入 + 1 输出、全历史重放、
  round-barrier、`--request-rate 16 --max-parallel 4 --seed 42
  --ready-queue-policy random --disable-random-sample --disable-auto-run`；
  每轮新增 ~41,000 prompt tokens。
- 现象（3 次独立复现，第 3 次数据）：r8 总命中 87.4%（L1 17.8 / L2 69.6 /
  L3 0%）→ r10 64.0%（13.5/35.2/15.3）→ r11 65.3% → r12 起恢复 80.1%，
  r12–r20 L3 贡献 52.6–74.2%；TTFT 0.63 s（r8）→ 1.78 s（r10）→ 2.13 s（r12）。
  tier 百分比定义 = 该层命中 prompt tokens / 该轮总 prompt tokens，
  L1+L2+L3 = 总命中率。
- 时间相关观测（banfeb 标注"仅时间相关，非因果"）：首次 Mooncake 内存
  驱逐发生在 r9 首请求完成后 0–2 s（三次运行一致）；约 1 s 后出现首个
  近全 miss 的全历史 L3 查询（`start=0`，9,216 tokens 只中 896，即 14 页
  中的前几页）；首个 `cached_tokens=0` 请求再晚数秒完成。无失败请求/
  retraction/OOM。

### 1.2 维护者机制定调（xiezhq-hermann，2026-11-10）

- **容量算术**：host 池 325,568 tokens ≈ 8 轮 ×41K；从 r9 起历史不再装下，
  L2 必然驱逐。`cache` 模式下 host 内存是持久树管理层，压力驱逐 churn
  缓存前缀——小 host 池下的已知限制（#14056/#16909/#20535/#28614 →
  #34798 `buffer_only` 的动机）。
- **建议**：`--hicache-host-memory-mode buffer_only`（host 仅作 staging，
  容量层移到 storage），同 commit 同负载跑 `cache` vs `buffer_only` 是
  最有用的对比。
- **链断假设（明确标注为待验假设）**：`MooncakeStore.batch_exists` 在
  首个缺失 K/V 对象处截断连续前缀匹配——一条对话早期的一个对象被驱逐，
  其后所有页即使仍在存储也不参与该前缀命中；896/9,216 的采样符合此型。
- 写失败排除法：main 日志签名 `Write page to storage: N pages failed.`
  与 `HiCache backup failed after N tokens`，r8–r12 窗口（乃至全日志）
  均未出现 → 存储写失败路径不参与。

### 1.3 已完成的 cache vs buffer_only 对比（banfeb，2026-11-14）

- 同 commit `e4d4a9a7de`、同 A40、唯一差异 `--hicache-host-memory-mode
  cache` vs `buffer_only`，host 池同为 325,568 tokens；各 1 次独立运行。
- 结果：dip 显著缓解（r9 72.1→79.3、r10 68.9→74.5、r12 66.3→83.6 pp），
  **min 命中率 66.3% → 74.5%（+8.2 pp）**；buffer_only 下 L2 贡献恒 0，
  L3 主导；但残留 r9–r11 dip（低于理论上界约 10–16 pp），且 L3
  contiguous-prefix coverage 同步下凹（r8 84.4% → r10 68.1% → r12 82.9%）。
- **TTFT 两个已汇总采样点 buffer_only 反而更高**（r8 0.58→0.85 s；
  r20 4.47→4.75 s）；完整 20 轮 TTFT 序列、尾部时延、重复试验均未提供。
- 写失败签名两运行均为 0；Mooncake master `StagingSize` 恒 0。
- mynotwo 定调（2026-11-14/16）：命中率改善成立；时延收益未确立；
  可重复性、根因、资源节省未知；后续根因实验应另立问题定义。

## 2. 本仓推断与 main 兼容性审计（非 issue 原文）

### 2.1 dip 起始轮的容量算术（本设计的关键杠杆）

每轮新增 prompt ≈ 40 × 1024 = 40,960 tokens，累计历史 ≈ 41K × r。
L2 与 L3 **同为 48 GB** → 两者几乎**同轮**触顶（325,568/41,000 ≈ 7.9 →
r8/r9 边界），这是基线 dip 与首驱逐同时出现的算术原因，也是两个机制
纠缠不可分的根源。**解耦扫描**：L2 96 GB → L2 触顶 ~r17 而 L3 仍在 r9
触顶（A3 臂）；L3 96 GB → 反之（A4 臂）。由此把"L2 churn 分量"与
"L3 驱动分量"在时间轴上拆开——上游没人做过这个分离。

### 2.2 token 级等机制换算（0.5B 快扫臂的合法性）

host 池 token 容量与模型无关（token 槽位），只随 `--hicache-size` 字节
预算 / 每 token KV 字节变化。Qwen2.5-0.5B 每 token KV = 2×24×2×64×2 =
12,288 B → **`--hicache-size 4`（4×10^9 B）恰好给出 325,521 tokens**，
与 issue 的 325,568 几乎逐 token 相同；`--max-total-tokens 178752` 原样
保留（0.5B 下仅 2.2 GB 显存）。因此 0.5B 臂在 token 维度完整复刻 dip
算术，只压缩了字节数与 prefill 时长 → 用于多臂快扫；时延结论只从 4B
保真臂取。kvtier"0.5B 可控优先"原则在此以容量等价的方式满足。

### 2.3 main 上需要核实的点（跑前审计清单）

- `benchmark/hicache/bench_multiturn.py` 在 main 仍存在；issue 所用全部
  flag（`--num-clients --num-rounds --request-length --output-length
  --request-rate --max-parallel --enable-round-barrier --ready-queue-policy
  --seed --disable-random-sample --disable-auto-run --log-file`）已在
  main `789abb9be` 逐一确认存在（本设计核对过 argparse）。跑时另记脚本
  文件 sha256 防漂移。
- `cached_tokens_details{device,host,storage}`：main
  `managers/io_struct.py:1766` 仍存在；bench_multiturn 的每轮分层统计
  依赖它（或等价渠道），烟测确认字段实值非空。
- fast_file extra-config 键名：diff 报告列出 `max_size`、
  `evict_high_watermark`(0.95)、`evict_low_watermark`(0.85)、
  `min_free_space`、`read_workers` 等，目录键未核实——跑前以 main
  `storage/fast_file/` 接线为准（审计点）。
- `--hicache-size` 为 int GB（10^9 字节，banfeb 实测 48.01 GB 换算证实），
  覆盖 `--hicache-ratio`；main 参数注册在 `arg_groups/fields/memory.py`。
- main 新增的 L3 miss 重试梯（`--hicache-storage-prefetch-retry-
  poll-interval/-max-attempts` 默认 8/8）与 `storage_prefetch_
  unfulfilled_tokens_total` 的 11 个 reason（`metrics_collector.py:2311-
  2344`，含 `host_capacity/device_capacity/deadline/cache_admission_
  shortfall/...`）：本实验每轮采样该矩阵，用于检测 #49221 家族形态
  是否混入（§6）。
- mooncake extra-config/env 兼容性（保真臂）：issue 时代经 env 传参；
  main 是否仍读同一组 env 或改走 `--hicache-storage-backend-extra-config`
  需审计（#49221 用的是 extra-config JSON 形态）。

### 2.4 fast_file 与 Mooncake 的语义差异（设计取舍）

fast_file：每对象一文件 + 双水位后台 LRU + 原子发布；存在性检查走文件
系统。Mooncake：master 集中记账 + `batch_exists` 首失截断。**若链断
截断语义是 Mooncake 查询实现特有，fast_file 臂可能不出现 H_chain 分量**
——这不算失败：A4 臂若在 fast_file 上不改变 dip 而 Mooncake 保真臂改变，
恰好把"链断"定位到存在性查询语义本身。两种结果都在 §3 预写解读。

## 3. 假设与可证伪预测

**H_L2（L2 容量 churn 主导，维护者定调）**：`cache` 模式下 host 池相对
工作集过小，r9 起压力驱逐 churn 前缀，L2 贡献坍缩并拖低总命中率。

- P1（复现）：cache 臂存在 dip：r*∈[7,13]，min ≤ 峰值−10 pp，
  ≤4 轮内恢复 ≥ min+10 pp；L2 贡献从 r8 前峰值到 dip 底下降 ≥ 20 pp；
  TTFT p50 峰值 ≥ 2× dip 前。
- P2（剂效）：A3（L2 96 GB，L3 不变 48 GB）→ dip 起始轮移至 r17±2
  （325,568×2/41,000 ≈ 15.9，触发轮 16–18），或 r9–r11 窗口深度 ≤ 基线
  的一半；A2（buffer_only）→ min 提升 ≥ 5 pp（issue 实测 +8.2）。
- P3（负预测）：若 A3 的 dip 仍在 r9–r11 且深度不减 → H_L2 的容量算术
  解释被证伪，主因转向 L3 侧（或未建模因素）。

**H_chain（L3 驱逐链断贡献，维护者的待验假设）**：L3 容量驱逐使对话
早期对象消失，首失截断使该对话后续页全部失效；表现为 L3 贡献与
contiguous coverage 在 r9–r11 反常低。

- P4（剂效）：A4（L3 96 GB，L2 48 GB）→ L3 触顶移至 ~r17，r9–r11 的
  dip 深度 ≤ 基线一半，且 V2 时间线上首驱逐→首个近全 miss 的 Δ 推后
  或消失。
- P5（buffer_only 残留 dip 归因）：buffer_only 臂 r9–r11 残留 10–16 pp
  下凹若随 A4'（buffer_only + L3 96 GB）消失 → 残留分量归 L3。
- 负预测：A4 不改变 dip 深度/时刻，且 fast_file 目录审计显示对象在
  miss 时刻仍存在 → H_chain 在本后端证伪。
- **注意**：H_chain 的"首失截断"谓词是 Mooncake 查询实现属性；fast_file
  臂的 P4 结果按 §2.4 双读。

**若两者都不成立（未复现）**：cache 臂 20 轮命中率全程 ≥ 理论上界−5 pp
（上界 ≈ 1 − 1024/(r×1025+1024)），两次重复一致 → 记"本环境未复现"，
归因候选 = GPU/L3 后端/main 演进（§2.3 重试梯、容量仲裁都可能已改变
形态——参考 `docs/upstream/2026-11-20-memcache-diff-...md` 主题 2/4/5）。

## 4. 负载形状与臂表

负载固定复刻 issue（§1.1 参数逐字），变量只在服务端容量配置：

| 臂 | 模型 | host memory mode | L2 容量 | L3 后端 / 容量 | 检验 |
|---|---|---|---|---|---|
| B0-base | 0.5B | cache | `--hicache-size 4`（≈325K tok） | fast_file 48 GB | 复现 + P1 |
| B0-base ×2 重复 | 0.5B | 同上 | 同上 | 同上 | 可重复性 |
| B2-buffer | 0.5B | buffer_only | 同上 | 同上 | P2（+issue 对照独立复验） |
| B3-l2x2 | 0.5B | cache | `--hicache-size 8`（≈650K tok） | fast_file 48 GB | P2 剂效（dip→~r17） |
| B4-l3x2 | 0.5B | cache | `--hicache-size 4` | fast_file 96 GB | P4 剂效（L3 触顶→~r17） |
| F0/F2/F4 | Qwen3-4B | 复刻 B0/B2/B4 | `--hicache-ratio 2 --hicache-size 48` | fast_file 48 / 48 / 96 GB | 保真（含 TTFT） |
| M0/M2（可选保真） | Qwen3-4B | 复刻 | 48 | Mooncake 48 GB + SSD offload（§1.4 全参数） | 后端语义对齐 issue |

- 驱逐压力的制造方式：**不是**额外 E 流量，而是多轮累计历史按 ~41K/轮
  增长依次越过 L1（178,752 tok，r≈4.4 触顶）、L2、L3 容量——三条水位线
  的触顶轮由参数直接控制，这就是本实验的"压力旋钮"。
- L1 保持 `--max-total-tokens 178752` 不变（两模型都合法：0.5B 占
  2.2 GB，4B 占 24.6 GiB；L1:L2 token 比 ≈ 0.55 复刻 issue）。
- 每跑之间：重启服务 + 清空 L3 目录（fast_file）或重启 master + 清
  SSD 目录（mooncake）+ 确认启动日志 host pool 行。

## 5. 判定门禁（validate_results 风格）

结果包落 `bench/repro-47481/results/results-<arm>-<UTC>.json`，字段：
per-round 汇总（prompt tokens、L1/L2/L3 命中、TTFT p50/p95、完成/失败数）、
轮界 counter 快照、V2 时间线数据、服务快照、bench 脚本 sha256。

**G0 路径前提（不满足 → 无法判定）**

1. 启动日志 host pool 行与目标换算一致（0.5B：4 GB → 325,521±2% tokens；
   4B：48 GB → 325,568±2% tokens），写入结果包；
2. 800 请求全部完成，无 abort/失败；bench jsonl 逐请求含
   `cached_tokens_details`（缺失则门禁失败，进兼容性排查）；
3. 写失败排除（#47626 家族）：全日志 grep `Write page to storage:` 与
   `HiCache backup failed after` 零命中，且
   `sglang:hicache_storage_backup_failed_tokens_total` 增量 = 0；
4. 服务边界：TP=DP=PP=CP=1、`enable_hierarchical_cache`、`enable_metrics`、
   `enable_cache_report`、`hicache_write_policy=="write_through"`、
   `hicache_host_memory_mode` 与臂定义一致、`hicache_storage_backend`
   与臂一致；40 位 commit 记录；bench_multiturn.py sha256 记录；
5. 第 1 轮命中率 ≤ 5%（空缓存起步健全性，bench 自带冷启动语义）。

**G1 dip 复现成功（cache 臂，B0 与 F0 分别判定）**

1. 存在 r*∈[7,13]：min(总命中) ≤ r*前局部峰值 − 10 pp；
2. 恢复：r*+4 轮内总命中 ≥ min + 10 pp；
3. L2 贡献从其峰值（r≤9）到 dip 底下降 ≥ 20 pp；
4. TTFT p50 峰值（dip 窗）≥ 2× dip 前基线（仅 F0 判定；B0 只记录）；
5. B0 两次重复的 r* 相差 ≤ 2 轮且深度差 ≤ 5 pp。

**G2 机制归属（在 G1 成立的臂上）**

- H_L2 成立：B3 的 dip 起始轮 ∈ [14,20]（预测 16–18）或 B3 在 r9–r11
  深度 ≤ B0 同窗的 50%；且 B2 min ≥ B0 min + 5 pp。
- H_chain 证据（满足其一即"存在 L3 分量"，两者皆不满足则 dip 全归 L2）：
  a) B4 的 r9–r11 深度 ≤ B0 同窗的 50%，或 V2 显示 B4 首驱逐时刻推迟
  ≥ 5 轮；b) V2 中基线臂首驱逐→首个近全 miss 请求的 Δ ≤ 5 s 且该请求
  的 L3 对象在 miss 时刻经目录审计仍存在（fast_file 可判；Mooncake 臂
  需 master 侧对象清单）。
- 全不满足 → 如实记录"两机制均未获支持"，负结果留档。

**G3 复现失败**：cache 臂全程命中率 ≥ 上界−5 pp 且无 ≥10 pp dip，
重复一致 → "本环境未复现"，按 §3 末段归因候选写边界。

**无法判定**：G0 任一失败；或 dip 出现但 r* 不随任何容量臂移动且
TTFT 无同步抬升（形态不匹配，疑似其他回归）→ 留档并检查 main 近期
hicache 相关 commit。

## 6. 干扰隔离设计

**与 #49221（急性 admission 窗口型）的区分**：
- 负载结构：本实验无 flush、无 salt 游戏、单请求并发 ≤4（`--max-parallel
  4`）→ 在途集 4×（≤20K prompt）远小于 host 池，不构成 #49221 的触发
  条件；每轮采样 `storage_prefetch_unfulfilled_tokens_total` 全 reason
  矩阵，若 `cache_admission_shortfall` 在某轮突增（而非常见的容量原因），
  标注"#49221 形态混入"并把该轮单独析出，不计入 H_L2/H_chain 判定。
- 时间尺度：#49221 是相位内秒级；本实验 dip 是轮级（每轮数十秒）且
  由累计容量触顶驱动——r* 随容量臂移动与否即是判别器。

**与存储写失败（#47626/#39444 家族）的区分**：G0-3 的双日志签名 +
counter 已是上游认可的排除法；`hicache_write_policy=write_through`
显式固定（避免 `write_through_selective` 的 hit_count 门控与父链
contiguity 不变量造成的策略性不落盘，见 diff 报告主题 7）。

**与 L1 驱逐背景的区分**：L1 在 r≈4.4 已触顶并持续驱逐（预期背景），
不构成 dip 解释——dip 判定用的是 r8 前峰值到 r9–r11 的**增量**变化，
且 L1 贡献下降预期由 L2/L3 补偿（issue r8：L1 17.8 + L2 69.6）。

**GPU/后端差异的控制**：4B 保真臂与 issue 同模型同 L1/L2 token 数；
dip 若只在 Mooncake 臂出现而 fast_file 臂不出现，差异收敛到后端语义
（§2.4），此时 fast_file 臂结果仍有效（它回答"当前 main + 本地后端"
的行为），Mooncake 臂回答 issue 保真性。

## 12. 边界与风险

1. **上游占坑活跃**：mynotwo 已认领单卡+Mooncake 端到端验证（截至
   2026-11-16 他声明"暂不需额外实验"），banfeb 持续跟进；本实验若公开，
   定位须写成"非 Mooncake 后端独立复验 + 双因子容量分离"，公开前重查
   issue 现状（PLAN.md P4）。
2. fast_file 与 Mooncake 的存在性查询语义差异可能使 H_chain 在主臂
   不可复现（§2.4 已预写双读）；M 臂是闭合这个缺口的唯一途径，但依赖
   Mooncake 前置。
3. main 相对 `e4d4a9a7de` 的演进（重试梯、命中时分配 staging、容量
   仲裁、window-first 回收）可能移动或抹平 dip——G3 是合法结果，且
   本身就是对 main 的有用信号；不要把"main 行为不同"误写为"复现失败"。
4. 0.5B 臂删 parser flag、TTFT 语义弱化（§4、§10 已标注）；4B 臂显存
   ~35 GiB < 48 GiB，但需按卡实测微调 `--mem-fraction-static`（0.85–0.90），
   偏差入结果包。
5. bench_multiturn 的 ready-queue/调度细节在 main 可能微调（脚本 31 KB，
   argparse 已核对，行为未审计）——记录 sha256 + jsonl 全量留存，
   异常时与 issue 数据逐轮比对而非重跑争论。
6. 每跑 L3 数据量：4B × 20 轮 ≈ 820K tokens × 144 KiB ≈ 115 GB >
  96 GB 上限（B4/F4 必然驱逐，设计使然）；/data 500G 需在臂间清理，
  侧车 sampler 的目录枚举在 80 万对象级别可能变慢——采样间隔 2 s 起步，
  若单次枚举 >1 s 则退化为 5 s（执行者按此规则，无需再决策）。
7. 本实验不回答 TTFT 端到端取舍（buffer_only 的时延代价只记录不判定，
   对齐 mynotwo 的定调）；不覆盖 A40→4090 的绝对时延可比性。
