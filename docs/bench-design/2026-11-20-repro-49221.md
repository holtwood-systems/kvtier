## 0. 结论先行

本实验的**第一判定点不是"复现 issue 数字"，而是"main 上该机制是否仍然存在"**：
issue 基线是 `10be18dc`（sglang 0.5.20），而 main 在该区域已大改（见 §2.3），
修复 PR #49226 也已 open。因此实验产出三种同等有价值的结果：

1. main 上仍复现 → 独立确认机制仍在，为 #49226 提供 Go 侧证据；
2. main 上不复现（且能排除环境差异）→ 负结果留档，提示已合的前置改动
   （staging 命中时分配、容量仲裁、重试梯）可能已消除该窗口；
3. 无法判定 → 按失败分类如实归档（kvtier 方法论）。

## 1. 上游事实（issue/PR 页面明确写的）

以下全部来自 issue #49221 原文与 PR #49226 描述，未掺入本仓推断：

- **现象**：GLM-5.3-Flash，32 请求 × 6,100 input tokens，同一 prompt 文本、
  32 个互异 `cache_salt`。串行（concurrency=1）命中 188,416 cached tokens；
  并发 16 仅命中 64,768，rank-0 的
  `storage_prefetch_unfulfilled_tokens_total{reason="cache_admission_shortfall"}`
  增量 +88,320。issue 明确说明：该计数含重复 prefetch 尝试，
  **不是**去重后的重算 token 数。
- **七相位脚本输出**（seed → serial → burst16-a/b → burst32 → repeat32-a/b，
  每相位前 `/flush_cache`）：

  | phase | cached_tokens | shortfall Δ | mean_s |
  |---|---:|---:|---:|
  | seed | 0 | 0 | 0.80 |
  | serial | 188,416 | 0 | 0.25 |
  | burst16-a | 64,768 | 88,320 | 4.86 |
  | burst16-b | 76,544 | 76,544 | 4.65 |
  | burst32 | 123,648 | 11,776 | 4.02 |
  | repeat32-a/b | 123,648 | 11,776 | ~4.0 |

- **机制假设（issue 原文）**："L3 completion inserts host pages without
  retaining an eviction reference until admission, allowing another prefetch
  to evict them before load-back"——生命周期缺口：L3 prefetch 完成后插入
  host radix 树的页没有持有防驱逐引用，直到 admission；并发下后到的
  prefetch 把先到者尚未 admission 的页从 L2 驱逐。
- **报告环境**：SGLang `10be18dcfc466a2171b4892de214909a328ff737`、
  sglang 0.5.20 / sglang-kernel 0.4.10、4×H20、TP4/EP4、`--max-total-tokens 32768`、
  `--hicache-ratio 2.0`、`--hicache-write-policy write_through`、
  mooncake L3（loopback TCP，64 GiB provider，`prefetch_threshold:64`）、
  `--hicache-storage-prefetch-policy wait_complete`、
  `--max-running-requests 16`、`--chunked-prefill-size 2048`、
  `--disable-cuda-graph`。
- **PR #49226 修复要点**（open，未合）：在 host radix 树中 pin 已完成的
  prefetch 直到 prefill admission 或 decode load-back 结束（abort/teardown
  亦释放）；瞬态 host 容量压力下按 FIFO 排队确认的 storage 命中（仅当存在
  能释放容量的在途操作，否则回退）；disaggregated prefill 下回退而非等待；
  撤销排队 prefetch 前校验操作身份。
- 附加观察（同报告者、另一 1P2D 部署，非本实验复现对象）：L2 池满
  （1.156M/1.169M slots）时 admission-shortfall 计数 87 秒内 +0.91M tokens。

## 2. 本仓推断与 main 兼容性审计（非 issue 原文）

### 2.1 机制为什么随并发触发（推断）

- 每请求页对齐命中 ≈ 5,888 tokens（188,416/32；issue 页大小默认 64 的
  6,100-token 前缀页对齐结果）。host 池 = ratio 2.0 × max-total-tokens
  32768 = 65,536 tokens ≈ **只能容纳 ~11 个并发在途请求的前缀**
  （16×5,888 = 94,208 > 65,536）。串行时在途集 = 1×5,888 « host 池，
  旧页被逐无害（该请求已消费完毕）；并发时**在途集**本身超出 host 池，
  互相驱逐发生在"尚未 admission"的窗口内 → shortfall。这是把
  "稳态容量不足"与"在途窗口被逐"区分开的关键视角。
- 32 个前缀总数据 195,200 tokens 同样远超 host 池，但串行仍 100% 命中
  （issue 数字）——**证明单纯的 L2 稳态容量不足以造成命中损失**，
  排除最弱解释。

### 2.2 main 上计数器与发射点已核实（commit `789abb9be`）

- `python/sglang/srt/observability/metrics_collector.py:2311-2344`：
  `sglang:storage_prefetch_unfulfilled_tokens_total`，文档字符串明确
  "Attempt-level … not a final prefill cache-miss counter"。原因枚举
  （pre-create 的 label 值）：`below_threshold / host_capacity /
  device_capacity / device_covered / storage_transfer / deadline /
  anchor_lost / aux_window_trim / device_overlap /
  cache_admission_shortfall / already_cached`。
  语义注解：`cache_admission_shortfall` = "an L3-loaded L2 span was no
  longer reusable when cache-mode admission ran"。
- `python/sglang/srt/managers/schedule_policy.py`（main）：发射分流——
  `needs_host_load_back() and host_loaded_length < host_hit_length` 记
  `device_capacity`，否则记 `cache_admission_shortfall`。**两路都要采**，
  不能只看后者。
- 新增相邻计数器（main）：`sglang:storage_prefetch_deferred_tokens_total
  {reason=host_capacity|device_capacity}`、
  `sglang:storage_prefetch_hit_tokens_total`、
  `sglang:hicache_backup_dropped_tokens_total`。
- API 字段：`cached_tokens_details{device,host,storage}` 在 main
  `managers/io_struct.py:1766` 仍存在（`/generate` 的 `meta_info`）。

### 2.3 main 上相关区域已大改（来自本仓静态 diff，
`docs/upstream/2026-11-20-memcache-diff-6afee75f-to-main.md` 主题 2/3/4）

- prefetch 暂存从"查询期预分配、失败即弃"改为**命中时分配**、存储往返期间
  不占 host 内存；支持部分命中（`allocate_storage_hit(allow_partial,
  min_tokens, evict_host)`，失败先逐 host 再试）；
- 新增 `capacity.py` / `prefill_budget.py` 容量仲裁（`reclaim_for_load_back`
  等）；
- 新增 L3 miss 重试梯 `--hicache-storage-prefetch-retry-poll-interval/
  -max-attempts`（默认 8/8），超限"按设备现有内容放行 admission"——
  这可能把部分本应 shortfall 的形态改写成"部分命中后放行"，解读时
  必须与 `deadline` / 重试耗尽路径分开。
- **结论**：issue 数字不能直接当 main 的预期值；§5 门禁只锚定相对关系
  与原因归属，不锚定 64,768/188,416 这类绝对数。

### 2.4 与 GLM-5.3-Flash 的保真差距（推断）

GLM-5.3-Flash 在 issue 中 TP4/EP4 于 4×H20 运行，单卡 4090 不可行；
其为 MLA 家族的可能性使 host 页布局/复制路径与 GQA 小模型不同
（未核实架构细节）。本实验以**机制同构**（host 树生命周期 + L2 容量比）
为目标，不追求架构保真，偏差在 §7 边界中如实标注。

## 3. 假设与可证伪预测

**H1（issue 假设在 main 上的存续）**：cache 模式下，L3 prefetch 已插入
host 树的页在 admission 前无防驱逐保护；当"并发在途集 × 每请求命中页"
超过 host 池自由容量时，页被其他 prefetch 驱逐，admission 时表现为
部分命中/未命中，`cache_admission_shortfall` 计数增长、cached_tokens 下降。

**若 H1 为真，应观察到**：

- P1 串行相位：shortfall（全原因）≈ 0，每请求 cached ≥ 0.9 × 页对齐上限
  （issue：5,888/6,100 = 96.5%）；
- P2 burst 相位：cached_tokens 总和显著低于串行（issue 幅度：降至 34–41%），
  且 `cache_admission_shortfall` 正增量并主导该相位 unfulfilled 总量；
- P3 剂效关系：固定 prefix 与 host 池，shortfall 随并发度 1→4→16→32
  单调上升，拐点在 在途集 ≈ host 池自由容量 处（c* ≈ host_free/5,888）；
- P4 host 池放大臂（host ≥ 2×32×5,888 ≈ 377K tokens）：shortfall 消失、
  cached 恢复至串行水平的 ≥ 90%；
- P5 TTFT 佐证：burst 相位平均/中位延迟高于串行 ≥ 3×（重算 6,100-token
  前缀的代价；issue：4.86 s vs 0.25 s）。

**若 H1 为假（main 已不复现），应观察到**：

- N1 所有 burst 相位 cached ≥ 0.9 × 串行，且全相位、全原因 unfulfilled
  增量 < 1 页（64 tokens）；
- N2 两次独立重复（服务重启 + 重新 seed）方向一致。

P3/P4 与 N1/N2 互斥；P1 不成立（串行都不命中）则路径有问题，判
"无法判定"并走失败分类。

## 4. 负载形状

复刻 issue 的七相位结构（这是它的全部负载，无显式 E 阶段——并发 prefetch
本身即是驱逐压力源）：

| 参数 | 判定臂（Qwen3-4B） | 探索臂（Qwen2.5-0.5B） | 说明 |
|---|---|---|---|
| 请求数 | 32 | 32 | 互异 salt，同一 prompt 文本 |
| prefix tokens | 6,100 | 6,100 | 页对齐命中 ≈ 5,888（page 64） |
| max_new_tokens | 1 | 1 | 温度 0，仅计时 prefill 路径 |
| 相位 | seed / serial / burst16-a / burst16-b / burst32 / repeat32-a / repeat32-b | 同左 | 非 seed 相位前 sleep 5 s + `/flush_cache` |
| 并发度 | 1 / 16 / 16 / 32 / 32 / 32 | 1→4→8→16→32 梯度 | 梯度供 P3 剂效曲线 |
| host 池 | `--hicache-ratio 2.0` + `--max-total-tokens 32768` → 65,536 tokens（≈9.4 GiB @144KiB/tok） | 同参数（≈0.8 GiB @12KiB/tok） | 复刻 issue 比例；在途集 16×5,888=94,208 > 65,536 |
| host 池放大臂 | `--hicache-ratio 12`（→393K tokens） | `--hicache-ratio 12` | 验证 P4 |
| 驱逐压力来源 | 并发 prefetch 在途 host 页集 > host 池 | 同左 | 无 E 阶段；L3 数据 32×5,888 tokens ≪ /data 容量，L3 侧无驱逐 |

容量算术（判定臂）：Qwen3-4B FP16 每 token KV = 2×36×8×128×2 = 147,456 B；
device 池 32,768 tokens = 4.6 GiB（显存总占用 权重 8 GiB + KV 4.6 GiB +
运行时 ≪ 48 GiB）；host 池 65,536 tokens = 9.4 GiB（1TB 内存无压力）。

## 5. 判定门禁（validate_results 风格，全部量化）

结果包按 kvtier 习惯落 `bench/repro-49221/results/results-<UTC>.json`
（schema 参照 `bench/repro-31600`，`benchmark` 字段改为
`sglang-hicache-admission-shortfall`），审计器逐条复核：

**G0 路径前提（任一不满足 → 无法判定，进入失败分类）**

1. seed 相位后 `sglang:backuped_tokens_total` 增量 ≥ 32 × 5,888（L3 写入
   完成；等待 backup 队列 drain 收敛，复用 workload.py 的静默收敛轮询）；
2. serial 相位 ≥ 31/32 请求 `cached_tokens_details.storage > 0`（L3 命中
   路径存在；flush 未清 L3 的前提由此反证）；
3. 独立 salt 冷探针（P 语义）在 flush 后 `sum(cached_tokens_details)==0`；
4. 服务快照满足：TP=DP=PP=CP=1、`enable_hierarchical_cache`、
   `enable_metrics`、`enable_cache_report`、
   `hicache_write_policy=="write_through"`（排除 selective 门控陷阱）、
   `hicache_host_memory_mode=="cache"`、
   `hicache_storage_backend` 与预期一致；40 位 SGLang commit 已记录。

**G1 复现成功（H1 在 main 成立）——须同时满足**

1. serial：全原因 unfulfilled Δ = 0，且每请求 cached ≥ 0.9×5,888；
2. ≥2 个 burst 相位：cached 总和 ≤ 0.75 × serial 总和
   （issue 实况 0.34–0.66，取保守阈值）；
3. 同批相位 `cache_admission_shortfall` Δ > 0 且 ≥ 该相位全原因
   unfulfilled 总量的 50%；
4. `host_capacity`、`device_capacity`、`storage_transfer`、`deadline`
   在 burst 相位增量均 ≤ 1 页/token 级噪声（< 64 tokens）——排除
   分配失败与传输错误两类替代解释；
5. 两次独立重复（重启服务重 seed）方向一致（门禁 1–4 同向成立）。

**G2 复现失败（main 已不复发）——须同时满足，作为负结果留档**

1. 所有 burst 相位 cached ≥ 0.9 × serial；
2. 全相位全原因 unfulfilled Δ < 64 tokens；
3. 两次独立重复一致。
   → 结论写法："在本机、本模型、`789abb9be` 上未复现 #49221 的
   admission-shortfall 形态"，并核对当期 main 是否已合 #49226/#48848
   家族（公开评论前必须重查上游状态）。

**G3 无法判定**：G0 失败；或 `host_capacity` 在 burst 中主导（压力落在
staging 分配而非 admission 生命周期——按 §6 隔离设计调大 ratio 后重跑一次，
仍主导则如实归档）；或出现 storage 读错误/abort。失败分类枚举沿用
workload.py 的 `config / not_backed_up / index_evicted /
storage_read_failed / transfer_anomaly / unknown`，新增
`admission_shortfall` 作为 G1 成立时的正向标注。

## 6. 干扰隔离设计

**要证伪的替代假设 A："L2 稳态容量不足"**（#47481 家族的慢性容量效应）
- 串行相位即对照：32 前缀总量 195K tokens 同样远超 host 池 65K，串行仍
  全命中（P1）→ 稳态容量本身不损失命中；
- 剂效臂 P3/P4：shortfall 应以"在途集/host 自由容量"为尺度出现阈值行为；
  稳态容量效应的剂量是累计写入量，不呈现该尺度；
- 计数器分流：稳态容量压力在 main 上应表现为 `host_capacity`（分配失败）
  而非 `cache_admission_shortfall`，G1-4 强制两者分离。

**要证伪的替代假设 B："L3 侧数据丢失/链断"**（#47481 的 chain-break）
- 本负载 L3 总量 ≈ 2.3 GB（0.5B 臂）/ 27 GB（4B 臂 @144KiB），`/data`
  500G，file/fast_file 后端无容量驱逐压力 → L3 侧驱逐不存在；
- seed 后记录 storage 目录页文件快照（`storage_dir_snapshot` 复用），
  burst 相位后快照不变 → L3 数据未动；
- 串行相位反复全命中（repeat 相位再验）→ L3 键/内容完好。

**要证伪的替代假设 C："flush 语义跨版本漂移"**
- 冷探针（G0-3）+ serial 命中（G0-2）双向夹逼：flush 清了 L1/L2
  （探针 0 命中）且没清 L3（serial 命中）。

**要证伪的替代假设 D："重试梯放行造成的假部分命中"**（main 新路径）
- 记录每相位 `deadline` 与重试相关增量；若 burst 的 cached 恢复伴随
  `deadline` 主导，说明是重试梯形态而非缺口修复，单独归类不并入 G2。

**buffer_only 对照臂**（机制归属，非判定门禁）
- `--hicache-host-memory-mode buffer_only`：host 无树驻留，PR #49226
  自述修复针对 cache 模式；预测 buffer_only 下 `cache_admission_shortfall`
  语义不适用/增量 ≈ 0。若 buffer_only 也增长同因 shortfall，
  机制描述需要修正（有价值的信息）。

**policy 对照臂**：`wait_complete`（主，issue 同款）vs `timeout`
（#47481 用）——prefetch→admission 窗口长度不同，shortfall 幅度应随之
变化（窗口越长越易被逐）。方向相反则 H1 存疑。

## 9. 可视证据采集方案（答辩用：指时间线讲根因）

**V1 host 水位 × shortfall 时间线（主证据，每个判定臂必采）**

- 工具：客户端内建连续采样器（附录 A 的 `reason_snapshot`/
  `counter_snapshot` 在相位之间以 1 Hz 连续调用即为数据源）+ matplotlib
  离线出图（不占 GPU 时间）。
- 采样范围：seed 开始前 30 s → 最后相位结束后 30 s，全程不断。
- 图面规格（执行者照画，不再决策）：x=墙钟；通道 1 =
  `sglang:hicache_host_used_tokens` 与 `_total`（gauge 水位线，total 画
  虚线）；通道 2 = `storage_prefetch_unfulfilled_tokens_total` 各 reason
  的累计增量阶梯线（`cache_admission_shortfall` 加粗置顶，其余变淡堆叠）；
  通道 3 = 每请求完成时刻散点（y=该请求 cached_tokens；绿=全命中
  ≥5,300、黄=部分、红=零/<1 页）；相位边界与 `/flush_cache` 时刻垂直
  虚线并标相位名；水平点线 = 理论在途容量 c* = host_free/5,888。
- 预期特征（H1 真）：serial 段水位锯齿（~5,888 上台阶、消费后回落）、
  shortfall 阶梯平坦；burst 段水位**贴满 total**、`cache_admission_
  shortfall` 阶梯同窗陡升、散点分裂为 5,888 与低位两簇。答辩讲法：
  "贴满的水位线 + 同一窗口的 shortfall 阶梯 = 在途页互相驱逐的直接
  时间线证据；串行段同容量下全命中排除稳态容量解释"。
- 若 G2 成立（main 不复现）：全部相位水位锯齿、全 reason 阶梯平坦、
  散点单簇——同一张图反向陈述"缺口已闭合"。

**V2 kernel 时间线（机制证据，4B 判定臂基线运行 1 次）**

- 工具：SGLang 内置 profiler（HTTP 控制，无需重启服务；字段名以 main
  `entrypoints/http_server.py` 的 `/start_profile` 定义为准，跑前核对
  一次）：

  ```bash
  curl -X POST http://127.0.0.1:30021/start_profile -H 'Content-Type: application/json' \
       -d '{"output_dir":"/data/prof/repro-49221/serial-burst","activities":["CPU","GPU"]}'
  # 客户端单相位模式依次执行：1 个 serial 相位 → flush → 1 个 burst16 相位
  curl -X POST http://127.0.0.1:30021/stop_profile
  ```

- 采样范围：仅 serial + burst16 各一次（对照内嵌同一 trace）；只在 4B
  判定臂做（0.5B 页太小、copy 段过短不具可读性）。
- 图/标注（chrome trace / perfetto 视图）：按请求分组，逐请求标注
  a) H2D 回载 copy 段（hicache transfer 类 kernel，位于 copy stream），
  b) copy 结束 → prefill 首个 compute kernel 的间隙，c) 纯 prefill
  compute 段长度；汇总"无前置 copy 段的请求占比"并与 V1 同窗的
  shortfall 阶梯对齐引用。
- 预期特征（H1 真）：命中请求 = copy 段 + 短 prefill；shortfall 请求 =
  无 copy 段 + 长纯 prefill。copy stream 与 compute stream 的重叠形态
  （admission 前回载是否与其他请求 prefill 重叠）一并截图备查。
- 备选（仅当 profiler 开销使 V1 形态失真时）：专用剖面运行
  `nsys profile --trace=cuda,osrt -o repro-49221-burst16
  python -m sglang.launch_server <§7 同参数>`，只跑 seed+serial+
  burst16 三相位；剖面运行不用于门禁判定。

**V3 全程旁证**：`nvidia-smi dmon -s pucmt -d 1 -o T -f dmon.log` 后台
常开——serial 段 PCIe H2D（回载）密集、burst 段稀疏（回载未发生），
与 V1/V2 互证；不单独作判定证据。

   归属问题在 main 已有针对性修复（cache_salt 显式传递 + exists 语义），
   但**仍需 G0 全部通过才允许进入判定**；若 G0-2（serial storage 命中）
   失败，先按 `index_evicted` 分类排查，不得直接判 G2。
4. mooncake 臂的 `prefetch_threshold:64` 等键是否仍被 main 接受未审计；
   file/fast_file 的目录参数键名待跑前核对（§7 审计点）。

   它们与 `cache_admission_shortfall` 强制分流。
